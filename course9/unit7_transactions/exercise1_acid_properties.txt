ACID Properties - What Database Transactions Guarantee

ATOMICITY
---------
All or nothing. Transaction either fully succeeds or fully fails.

Example: Transfer $100 from Alice to Bob
1. Deduct $100 from Alice's account
2. Add $100 to Bob's account

If step 2 fails (power outage, crash, etc.), step 1 is rolled back.
Money doesn't disappear. No partial transactions.

Without atomicity: Alice loses $100, Bob doesn't get it. Bad.
With atomicity: Both updates happen, or neither does. Safe.


CONSISTENCY
-----------
Database stays in a valid state. Constraints are enforced.

Example: Account balance can't be negative
Transaction tries to withdraw $1000 from account with $500.
Database rejects it - violates constraint.

Ensures business rules are never broken.


ISOLATION
---------
Concurrent transactions don't interfere with each other.
Each transaction sees consistent data.

Example: Two people booking last airline seat
- Transaction A: Check seats available (1 seat)
- Transaction B: Check seats available (1 seat)
- Transaction A: Book seat
- Transaction B: Book seat  ← Should fail!

Without isolation: Both book the same seat (overbooking).
With isolation: Second transaction sees seat is taken, fails.

(Isolation levels control how strict this is - covered in exercise 4)


DURABILITY
----------
Once transaction commits, changes are permanent.
Survives crashes, power failures, etc.

Example: Transfer money, transaction commits
Immediately after, server crashes.
When server restarts, the transfer is still there.

Database writes to disk and logs to guarantee this.


WHY ACID MATTERS
----------------
Banking: Money transfers must be atomic
E-commerce: Inventory counts must be consistent
Bookings: Tickets/reservations can't be double-sold
Any critical operation where data integrity matters


NON-ACID SYSTEMS
----------------
Redis (cache): Fast but no durability guarantees
MongoDB (older versions): Had weak consistency
NoSQL databases: Often trade ACID for speed/scalability

Use ACID databases (PostgreSQL, MySQL) when correctness > speed.
Use non-ACID systems when speed > perfect consistency (caching, logs).


REAL-WORLD EXAMPLE
------------------
E-commerce checkout:
1. Verify items in stock
2. Create order record
3. Decrement inventory
4. Charge payment
5. Send confirmation email

Wrapped in transaction:
- If payment fails, order is not created and inventory not decremented
- If server crashes during step 4, steps 1-3 are rolled back
- All or nothing

Without transaction:
- Inventory decremented but payment fails - you lose inventory
- Order created but inventory not decremented - you oversell
- Chaos


THE BOTTOM LINE
---------------
ACID transactions prevent data corruption.
Use them for anything where correctness matters.
They're not free (performance cost), but they prevent disasters.
